# Description 最適化ガイド

トリガー条件の原則は `ref-agent-skill §3`「description はモデル向けトリガー条件」を参照。本ファイルは run-skill-creator Step 6 固有の **手順テンプレート** に集中する: ① 2 落とし穴の回避、② 3 タイプ Before/After による再構成、③ トリガー eval クエリの作成。

## 2 つの落とし穴

### 落とし穴 1: 動作の手順を書いてしまう

詳細と obra/superpowers の事例 (`code review between tasks` で本文 2 段が 1 段しか動かなかった件) は `ref-agent-skill §3` 「description はモデル向けトリガー条件」に既出。本ファイルでは結論のみ:

description は **いつ呼ぶか** だけに絞る。「採点する」「JSON で返す」「複数段並列実行する」のような動詞・処理の流れ・段数を description に出さない。**呼ばれて何をするか** (手順・段数・形式・出力 schema) は本文に置く。

### 落とし穴 2: 発動ワードを並べすぎる

3 個以上並べると次のどちらかに化ける:

- (a) **重複** — 「スキル設計の採点」「SKILL.md の評価」のような言い換え
- (b) **処理の流れの紛れ込み** — 「複数パターン」「JSON で返す」のような動作説明 (落とし穴 1 と同根)

上限は **2 個前後**。`description` + `when_to_use` の合算は **1,536 文字 cap** で、Skill 一覧全体もコンテキスト予算に圧迫されるため短く保つ。

## 3 タイプの Before / After

| タイプ | Before (人間向け要約) | After (発動条件) | 何が違うか |
|---|---|---|---|
| `ref-*` | `API の規約集です。エンドポイント設計や OpenAPI レビューで参照します。` | `「API規約」「OpenAPIレビュー」で発動。REST/OpenAPI 規約のための ref。` | After は発動ワード 2 個 + 何のための ref かを明記 |
| `assign-*-evaluator` | `Skill を評価するスキル。SKILL.md の品質を採点します。` | `「skill レビュー」「SKILL.md 採点」で発動。ref-agent-skill に基づく Skill 設計の evaluator。` | After は採点根拠 ref と役割 (evaluator) を明示 |
| `wrap-*` | `サムネイルを複数パターン生成するスキル。` | `「サムネ作って」「サムネイル生成」で発動。run-thumbnail の wrap。` | After は発動ワード 2 個 + 派生元 base を明記 |

3 タイプに共通する破綻パターン:

1. **発動ワードがない or 多すぎる** — Claude がユーザー発話と照合する「鍵」が無い、または 3 個以上並べて重複・手順紛れ
2. **役割・派生元・採点根拠が見えない** — `assign-*-evaluator` なら採点根拠 ref、`wrap-*` なら派生元 base を frontmatter の 1 行で示す
3. **動詞・段数で動作説明が混じる** — 「採点する」「JSON で返す」「4 枚並列実行する」を書くと落とし穴 1 を踏む

description を書き直す作業は **この 3 点を埋めるだけ** で済む。文章を膨らませる必要はない。

## トリガー Eval クエリの作り方

description の品質を測るために should-trigger / should-not-trigger テストクエリを作る。**質に倒す** — 数を並べるより near-miss の濃度を上げる。

### Should-trigger (4-6 個、うち near-miss 最低 2)

- 同じ意図の異なる表現 (フォーマル〜カジュアル)
- スキル名やファイルタイプを明示しないが、明らかにそのスキルが必要なケース
- 他スキルと競合するが勝つべきケース

### Should-not-trigger (4-6 個、うち near-miss 最低 2)

**最も価値があるのは near-miss** — キーワードや概念が重なるが、実際は別の対応が必要なもの。

| NG (簡単すぎる) | OK (near-miss) |
|---|---|
| 「フィボナッチ関数を書いて」(PDF スキルの negative) | 「この PDF の表をコピペしたい」(抽出スキルではなく手動コピー) |
| 「天気を教えて」 | 「この CSV をグラフにして」(ダッシュボードではなく単発チャート) |

### クエリの品質

- 実際のユーザーが打つ文面 (具体的なファイル名、文脈、略語、タイポ、カジュアル)
- 長さを混ぜる
- 明確なケースより境界ケースに集中する

**悪い例**: `"データをフォーマットして"` / `"PDF からテキスト抽出"` / `"チャートを作成"`

**良い例**: `"上司からさっき来たxlsx (ダウンロードにある、Q4売上最終版v2.xlsx みたいな名前) に利益率の列を追加したいんだけど、売上がC列でコストがD列だったと思う"`

## 最適化の流れ

1. 現在の description で should-trigger / should-not-trigger クエリを作る
2. ユーザーにクエリセットを確認してもらう
3. 誤判定があれば description を 3 タイプ Before/After 表に従って修正
4. 修正後の description を before/after で提示
