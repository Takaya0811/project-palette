# コンテキスト収集ガイド（Phase 0 詳細）

Phase 0 でソース素材を収集・統合する際の詳細手順。
SKILL.md の Phase 0 セクションから参照される。

---

## URL入力の処理手順

### Step A: 生HTML取得

`curl -sL <URL>` (Bash) で生HTMLを取得し `output/{name}-raw.html` に保存。

**WebFetch は内部でAIモデルが要約するため、詳細データ・図表・画像URLが欠落する。必ず curl を先に実行すること。**

### Step B: 画像URL抽出・ダウンロード

生HTMLから `<img src="...">` / `<link rel="preload" as="image">` を抽出し、
記事内で使われている画像を `output/{name}-asset-{nn}.{ext}` にダウンロード:

```bash
# 例: img タグの src を抽出（相対URLはベースURLを付与）
grep -oP '(?<=src=")[^"]+\.(png|jpg|jpeg|gif|webp|svg)' output/{name}-raw.html | sort -u
```

### Step C: テキスト整形

生HTMLからMarkdownへの変換は以下の優先順位で行う:
1. 生HTMLを自分で読み取り、手動でMarkdown化する（最も正確）
2. WebFetch を補助的に使い、要約ではなく構造の参考とする

### Step D: 補完チェック

生HTMLの内容と source.md を突合し、漏れている数値・引用・セクションがないか確認。

### ブラウザ系ツール

agent-browser スキルまたはブラウザMCPツールが利用可能な場合はそれも活用する（動的レンダリングが必要なSPAサイト等で有効）。

## 混合入力の処理手順

混合入力は最も多いパターン。Slack議論、会議メモ、URL、箇条書きなどが散在する場合の手順:

### Step A: 素材一覧化

まず全入力を種類別に整理する:

```markdown
## 素材一覧
| # | 種類 | ソース | 概要 |
|---|------|--------|------|
| 1 | URL  | https://... | ブログ記事 |
| 2 | テキスト | ユーザー入力 | 会議メモ（箇条書き） |
| 3 | ファイル | docs/spec.md | 仕様書の一部 |
| 4 | テキスト | ユーザー入力 | Slack議論の抜粋 |
```

### Step B: 各素材を取得

URL は URL手順で、ファイルは Read で、テキストはそのまま。

### Step C: 統合・構造化

散在する素材を **1つの論理構造** にまとめる:
1. **重複排除**: 同じ情報が複数素材に含まれていたら1つに統合
2. **時系列整理**: 議論や意思決定の経緯があれば時系列に並べ替え
3. **主張抽出**: 散在するメモから **核となる主張・結論・データ** を抜き出す
4. **ギャップ特定**: 素材間で矛盾していたり、説明が足りない箇所を特定

### Step D: ギャップ補完

Step C でギャップが見つかった場合:
- ユーザーに質問して補完する（AskUserQuestion で最大3問）
- 質問例: 「〇〇について△△と□□の2つの見解がありますが、どちらが最終結論ですか？」
- 質問例: 「〇〇のデータ・根拠はありますか？あればスライドの説得力が増します」

### Step E: source.md 作成

統合結果を以下のテンプレートで構造化された source.md として保存:

```markdown
# {タイトル}
Source: 混合入力（{素材数}件）
Chars: {文字数}

## コンテキスト概要
- 背景: {なぜこのプレゼンが必要か}
- 対象者: {誰に向けるか — 素材から推測 or ユーザーに確認}
- ゴール: {聴衆に何をしてほしいか}

## 主要な主張・結論
1. {核となるメッセージ1}
2. {核となるメッセージ2}
3. ...

## 裏付けデータ・事実
- {具体的な数値・引用・事例}

## 詳細
{素材を論理順に統合した本文}
```

## 画像素材の収集

- URL入力の場合: **Step B で既にダウンロード済み**の画像を使用
- 全入力タイプ共通: ソース内の追加画像URLがあれば `output/` に保存
- ユーザーが提供した画像ファイルがあれば `output/` にコピー
- 各画像に対して **何が写っているか・どの文脈で使われているか** を記録する
- **既存画像はAI生成画像より優先**してスライドに組み込む（引用・出典として信頼性が高い）
- 既存画像を使う場合は出典（元記事タイトル・URL等）をスライド内に小さく記載

---

## source.md の出力フォーマット

```markdown
# {タイトル}
Source: {URL or file path or "mixed input (N件)"}
Chars: {文字数}

## 利用可能な画像アセット

| ファイル | 内容 | 元の文脈 | 推奨用途 |
|---------|------|---------|---------|
| output/{name}-asset-01.png | {何が写っているか} | {元記事のどのセクションで使われていたか} | {スライドでの使い方の提案} |

※ 画像がない場合はこのセクションを省略

---

{本文}
```

**Chars は `wc -m` で計測して必ず埋めること。** Phase 1 のスクリプトに渡す値と一致させる。

## WebFetch の限界

WebFetch はAIモデル経由でコンテンツを処理するため:
- **長文記事が要約される** — 数値データ・引用の文脈・具体例が省略される
- **画像URLが消失する** — HTML内の画像タグ情報が返されない
- **表・コードブロックの忠実性が低い** — 構造が簡略化されることがある

したがって **curl による生HTML取得を主、WebFetch を従** とする。
WebFetch は「記事の概要把握」や「curl で取れない動的サイトの補完」に使う。

## ソース品質チェック（Phase 1 開始前ゲート）

Phase 1 に入る前に以下を確認する:

- [ ] `output/{name}-source.md` の文字数が **元URLの記事として妥当な量** か
  - 一般的なブログ記事なら 3000文字以上、論文・レポートなら 10000文字以上が目安
  - 極端に少ない場合（元記事の1/3以下と推測される場合）は Phase 0 をやり直す
- [ ] 画像アセットが取得されているか（画像を含む元記事の場合）
- [ ] source.md 内に具体的なデータ・数値・引用が含まれているか（元記事に存在する場合）

品質が不十分な場合は Phase 0 に戻り、curl での再取得や関連URLの追加取得を行う。

## density 選択ガイド

| density | 倍率 | 使いどころ |
|---------|------|-----------|
| `compact` | ×0.7 | 社内共有・要点のみ伝えたい場合。ユーザーが「簡潔に」と言った場合 |
| `standard` | ×1.0 | デフォルト。大半のケースに適用 |
| `detailed` | ×1.3 | 教育・チュートリアル系。段階的な説明が必要な場合 |
| `rich` | ×1.6 | 研究発表・データ重視。数値・引用・グラフを漏らさず含めたい場合 |

ユーザーの指定がなければ、ソースの性質から自動判断する:
- 数値データ・研究引用が多い → `detailed` or `rich`
- ブログ・エッセイ系 → `standard`
- 議事録・メモの箇条書き → `compact`

**`isLow: true`（12枚以下）の場合 → AskUserQuestion で確認:**

> 見積もり結果は **{slides}枚** です（ソース文字数: {chars}）。
> コンテンツが少なめのため、以下から選んでください:
> 1. **このまま進める** — コンパクトなスライドを作成
> 2. **関連情報を追加** — URL・ファイル・テキストを追加で提供してください
> 3. **インタビューで補完** — 私から質問してコンテンツを膨らませます
